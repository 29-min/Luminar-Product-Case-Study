# 설계 결정과 문제 해결

## 운영비와 관리 부담을 줄이는 구성

동아리에서 유지할 수 있도록 운영비 0원을 목표로 잡았습니다. 서버를 직접 관리하기보다 서버리스 배포를 고려했고, 화면과 API를 함께 다룰 수 있는 Next.js를 선택했습니다.

사진은 기존에 사용하던 Google Drive에 저장했습니다. 운영진에게 익숙한 폴더 구조를 유지할 수 있다는 장점이 있었습니다. 전용 이미지 저장소를 사용하면 파일 권한과 이미지 전달 방식을 더 세밀하게 설계할 수 있지만, 별도 자원과 운영 설정이 필요합니다.

무료 한도는 사용량에 따라 달라집니다. 실제 비용 절감액이나 지속적인 무료 운영 여부를 측정한 것은 아닙니다.

## GAS에서 업로드와 목록 조회 분리

초기 GAS 코드에서는 업로드 파일을 Base64로 전달하고, 사진 조회 시에도 이미지 데이터를 Base64로 반환했습니다. 대용량 사진을 다룰 때 인코딩·중계 부담이 있었습니다.

Next.js로 옮기면서 파일은 multipart로 전송하고, 목록 API는 파일 ID와 이름만 반환하도록 나눴습니다. 브라우저에서는 필요한 사진을 따로 읽습니다. 최적화 옵션으로 전송 전 이미지 크기를 줄이고, 여러 파일을 병렬 처리합니다.

다만 현재 운영 코드의 주요 사진 화면은 원본 프록시를 사용합니다. 목록 API를 가볍게 만드는 것과 이미지 자체를 작게 제공하는 것은 별도 과제입니다. 후자는 썸네일 생성과 저장·전달 구조 개선이 필요합니다.

## 직접 업로드 테스트의 CORS 오류

처음에는 서버가 Resumable Upload URL만 발급하고, 브라우저가 Drive에 직접 `PUT` 요청을 보내도록 설계했습니다. 파일이 서버를 거치지 않도록 하려는 의도였습니다.

URL 발급 요청은 성공했지만, 파일 전송 단계에서 `No Access-Control-Allow-Origin` 오류가 발생했습니다. 당시 테스트 환경에서는 이 경로로 업로드를 완료할 수 없었습니다.

서버가 FormData를 받아 `drive.files.create`로 업로드하도록 바꿨습니다.

```text
초기: 브라우저 → 서버에서 URL 발급 → 브라우저가 Drive로 PUT
변경: 브라우저 → Next.js에서 파일 수신 → Drive 업로드
```

서버 중계로 업로드 문제를 해결한 대신 서버가 파일 전체를 Buffer로 보유하게 됐습니다. 큰 파일을 다룰 때는 요청 크기, 실행시간, 메모리와 전송량을 함께 고려해야 합니다.

## Service Account 저장공간 오류

Service Account로 폴더를 만들 수는 있었지만 파일 업로드에서 다음 오류가 발생했습니다.

```text
403: Service Accounts do not have storage quota.
```

사용자 Drive의 저장공간을 사용할 수 있도록 OAuth2 Refresh Token 인증으로 변경했습니다. 서버가 API를 호출하므로 제출하는 회원의 개별 Google 로그인은 필요하지 않습니다.

이 방식은 연결 계정과 토큰에 의존합니다. 계정 변경이나 권한 철회에 대응할 수 있도록 설정을 관리해야 합니다.

## 루트 폴더를 찾지 못하는 문제

환경변수의 폴더명이 실제 Drive 폴더명과 달라 조회가 실패한 적이 있습니다. 이름을 일치시키는 것과 함께 루트 폴더 ID를 직접 지정하는 경로를 추가했습니다.

이름 조회는 설정하기 편하지만 이름 변경과 중복에 영향을 받습니다. ID를 지정하면 특정 폴더를 명확히 가리킬 수 있어 이 방식을 우선 사용하고, 이름 조회는 대체 경로로 남겼습니다.

## 동시 업로드의 폴더 중복 생성

같은 날짜와 조로 사진 두 장을 동시에 제출했을 때 폴더가 두 개 생겼습니다. 두 요청이 모두 ‘폴더가 없음’을 확인한 뒤 각각 생성하는 경쟁 상태(Race Condition)였습니다.

```text
요청 A: 폴더 조회 → 없음 → 생성
요청 B: 폴더 조회 → 없음 → 생성
```

사진 전송 전에 날짜·조 폴더를 먼저 준비하도록 분리했습니다. 폴더 생성 함수에서는 같은 `부모 ID + 폴더명`에 대한 Promise를 공유합니다.

```typescript
// 처리 흐름을 줄여 쓴 예시
const pending = new Map<string, Promise<string>>();

function getOrCreateFolder(parentId: string, name: string) {
  const key = `${parentId}::${name}`;
  if (!pending.has(key)) {
    const task = findOrCreate(parentId, name)
      .finally(() => pending.delete(key));
    pending.set(key, task);
  }
  return pending.get(key)!;
}
```

`findOrCreate`는 Drive 조회·생성을 나타낸 의사 코드입니다. 같은 프로세스의 동시 요청은 하나의 작업을 기다리게 됩니다. 여러 서버리스 인스턴스 사이에서 폴더의 유일성을 보장하는 방식은 아니므로, 운영 규모가 커지면 별도 중복 제어가 필요합니다.

## 파일명 기반 관리의 장단점

촬영 정보로 파일명을 만들면 Drive만 열어도 사진을 구분할 수 있습니다. Organizer의 명단과 Editor의 날짜·장소·참여자 정보를 채우는 데도 사용했습니다.

대신 구분자가 들어간 이름이나 장소를 처리하기 까다롭고, 정렬 순서를 영구 저장하기 어렵습니다. 다음 버전에서는 사진 ID를 기준으로 촬영 정보와 순서를 별도 저장하는 구조가 필요합니다.
