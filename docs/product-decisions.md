# Product & Technical Decisions

## 1. 먼저 해결할 업무: 제출과 다음 작업 사이의 단절

**맥락:** 회장이 단체방 사진을 내려받아 이름과 날짜를 바꾸고 Drive에 다시 올린 뒤, 디자이너가 내려받는 흐름이었습니다.

**결정:** 제출 시 날짜·조·이름·출사지 정보를 받고, 파일명과 폴더에 반영해 운영진의 조회와 제작 단계로 연결했습니다.

**이유:** 저장 공간을 새로 제공하는 것보다 제출 정보를 재사용하는 것이 반복 수작업을 줄이는 핵심이었습니다.

**한계:** 파일명에서 정보를 파싱하면 구분자·동명이인·장소 변경·검색에 취약합니다. 후속 버전에서는 구조화된 데이터와 별도 식별자가 필요합니다.

## 2. GAS로 시작하고 Next.js로 확장

**맥락:** 2024년에 GAS로 MVP를 제작했습니다. 당시 코드 사본에는 사진 Base64 처리와 Drive 폴더 관리가 있습니다.

**결정:** 업로드·화면 구성의 제약을 경험한 뒤 Next.js App Router 기반으로 확장했습니다.

**대안:** GAS를 계속 확장하거나, 독립 API 서버와 별도 프런트엔드를 구성할 수 있었습니다.

**트레이드오프:** Next.js는 UI·API를 한 프로젝트에서 관리하기 쉽지만, 이미지 중계는 서버 실행·전송 한도를 고려해야 합니다. 전환을 실제 측정되지 않은 성능 배수로 표현하지 않습니다.

## 3. 운영비 0원 목표와 서버리스 지향

**맥락:** 소규모 동아리에서는 운영비와 서버 관리 부담이 지속 운영의 제약이었습니다.

**결정:** 운영비 0원을 목표로 기존 Drive와 서버리스 배포를 고려한 구조를 선택했습니다.

**대안:** 전용 Object Storage, 관리형 DB, 독립 서버는 확장성과 데이터 모델 측면에서 유리할 수 있습니다.

**트레이드오프:** 무료 한도와 플랫폼 제약에 의존합니다. 실제 비용 0원 달성 여부는 청구·사용량 자료 없이 확정하지 않습니다.

## 4. Drive 직접 업로드에서 서버 중계로

**맥락:** 개발 로그에 브라우저에서 Drive로 직접 전송하는 방식의 CORS 문제가 기록되어 있습니다.

**결정:** Next.js에서 파일을 받아 Drive로 업로드하도록 변경했습니다. 현재 운영 코드 사본도 이 구조입니다.

**대가:** 브라우저 CORS 문제를 피하는 대신 서버가 파일 전체를 Buffer로 보유하고 중계합니다. 메모리·요청 크기·트래픽 문제가 남습니다.

## 5. Service Account에서 OAuth2로 복귀

**맥락:** Service Account 업로드의 저장공간 문제를 경험했습니다.

**결정:** 사용자 계정의 Drive 저장공간을 사용하는 OAuth2 Refresh Token 방식으로 복귀했습니다. 관련 커밋은 `89815e4`입니다.

**대가:** 계정과 토큰 수명 관리에 의존합니다. 토큰 값과 실제 계정 정보는 공개본에 포함하지 않았습니다.

## 6. 동시 업로드와 이미지 처리

**결정:** 폴더 초기화를 먼저 수행하고 사진을 병렬 처리하며, 동일 폴더 생성 Promise를 공유했습니다. 관련 커밋은 `2552a31`입니다. 선택적으로 Canvas 축소·JPEG 인코딩을 수행합니다.

**한계:** Promise 공유는 프로세스 범위입니다. 전체 서버리스 인스턴스의 유일성을 보장하지 않습니다. 기존 이미지 변환에는 MIME과 파일명 확장자 일관성 검토도 필요했습니다. 공개본은 실제 저장 형식에 맞춰 확장자를 생성합니다.

## 7. 유지보수와 콘텐츠 제작 연결

**결정:** 날짜·조 기준 조회, 제출자 명단 생성, 정렬 결과를 이용한 Editor 이동, 날짜·장소·명단 자동 입력, 표지와 사진 ZIP 내보내기를 연결했습니다.

**이유:** 운영자가 매번 파일명과 명단을 해석하고 다른 도구에 재입력하는 부담을 줄이기 위해서입니다.

**한계:** 영구 정렬, 역할별 계정, 공동 편집, SNS 자동 게시는 확인되지 않았습니다. 구현되지 않은 기능을 성과로 쓰지 않습니다.

## 8. 공개 데모의 별도 데이터 경계

**결정:** 비공개 저장소를 유지하고 Git 이력을 복사하지 않았습니다. 운영 API·인증·회원 데이터를 제거하고 IndexedDB 기반 데모를 별도로 만들었습니다.

**대안:** 기존 저장소를 정리해 공개하거나 서비스에 데모 계정을 제공할 수 있었습니다.

**이유:** 기존 사진·이름·계정의 공개 동의와 운영 자원 접근 문제를 분리하면서 제품 흐름을 보여주기 위해서입니다.

**대가:** 공개본으로 실제 다중 사용자 운영·서버 성능·Drive 연동을 검증할 수 없습니다. 공개본의 구현 차이는 문서와 화면 안내에 표시합니다.

## 9. Map 제외

Map은 제작자가 중단한 실험 기능입니다. 사진 제출·정리·콘텐츠 제작이라는 핵심 사용자 흐름에 집중하기 위해 공개본의 페이지·메뉴·자산·설명에서 제외했습니다. 기존 비공개 원본의 Map 코드는 보존했습니다.

## 후속 검증 계획

측정 자료를 확보한다면 제출 완료율, 실패·재시도, 사진 재분류 발생, 제출부터 SNS 제작 완료까지의 단계와 시간을 살펴보겠습니다. 디자이너·운영진 인터뷰와 함께 수집하되, 아직 측정한 결과처럼 표현하지 않습니다.
