# Technical Architecture

## 범위

이 문서는 기존 서비스에서 확인한 구조와 공개 데모의 구조를 구분합니다. 공개 데모에서 기존 Drive API나 운영 서버에 접근하는 경로는 없습니다.

## 기존 서비스

```text
회원 브라우저
  ├─ 날짜·조·이름·출사지·사진 입력
  ├─ 선택적 Canvas 리사이즈·JPEG 압축
  ├─ 폴더 초기화 요청
  └─ 사진별 multipart 요청을 병렬 전송
          ↓
Next.js Route Handlers
  ├─ 날짜/조 폴더 조회·생성
  ├─ 이름-순번-출사지 파일명 생성
  └─ OAuth2 인증으로 Google Drive API v3 호출
          ↓
Google Drive
  └─ 루트 / 날짜 / 조 / 사진

관리자 브라우저
  ├─ 폴더·사진 목록 조회 (이미지 Base64 대신 파일 ID)
  ├─ Next.js 이미지 프록시에서 이미지 수신
  ├─ Organizer에서 사진 정렬·명단 생성
  └─ Editor에서 Fabric.js 표지 제작 → JPG / JSZip 내보내기
```

### 인증 경계

Drive 접근은 서버의 OAuth2 Client Secret·Refresh Token으로 처리합니다. 회원 개별 Google 로그인은 아닙니다. 초기 Service Account 시도 후 저장공간 제약에 대응해 OAuth2로 복귀한 커밋이 있습니다. 관리자 접근 구분은 있었으나, 이 문서는 기존 세션 구현을 보안 설계 모범 사례로 제시하지 않습니다. 운영 인증 코드는 공개본에서 제외했습니다.

### 이미지와 동시성

- 실제 업로드는 서버를 거칩니다. 과거 문서의 브라우저 → Drive 직접 전송 구조는 현재 구조가 아닙니다.
- 기존 클라이언트는 최적화 선택 시 가로 폭을 1,920px 이하로 줄이고 JPEG quality 0.82로 인코딩합니다. 긴 변 기준 제한은 아닙니다.
- 업로드 목록은 `Promise.allSettled`로 처리하고 개별 성공·실패 수를 표시합니다.
- 폴더 초기화를 사진 전송 전에 분리하고, 같은 부모/폴더명의 생성 Promise를 공유합니다. 공유 범위는 서버 프로세스 내부입니다.
- 목록은 파일 ID만 반환하지만 현재 주요 사진 UI는 원본 프록시를 사용합니다. 모든 썸네일이 경량화됐다고 주장하지 않습니다.
- 정렬은 클라이언트 상태와 Editor URL, 다운로드 파일명의 순번에 반영됩니다. 서버에 정렬을 저장하는 구현은 확인되지 않았습니다.

## 공개 데모

```text
정적 호스팅 (Next.js export 결과)
  └─ HTML / JS / CSS / 샘플 SVG / 로고
           ↓
브라우저
  ├─ DemoProvider: IndexedDB 준비·초기화 안내
  ├─ UploadForm: 검증·선택적 이미지 축소
  ├─ demoFetch: UI 요청 형식을 로컬 저장소 동작으로 변환
  ├─ IndexedDB: 사진 Blob과 분류 정보
  ├─ Blob URL: 사진 미리보기·Fabric.js 입력
  └─ Fabric.js + JSZip: JPG / ZIP 다운로드
```

### 핵심 구현 위치

| 파일 | 책임 |
| --- | --- |
| `lib/demo-store.ts` | 가상 사진 초기값, IndexedDB 읽기·쓰기·초기화, Blob URL, 로컬 어댑터 |
| `components/DemoProvider.tsx` | 초기화 완료 전 화면 게이트, 저장소 오류 안내, 전체 초기화 |
| `components/UploadForm.tsx` | 사진 선택·검증·축소·병렬 저장·진행 상태 |
| `app/organize/page.tsx` | 폴더 선택, 사진 조회, 명단·다운로드, Editor 이동 |
| `components/PhotoGrid.tsx` | 그리드 정렬과 이미지 비율 표시 |
| `app/editor/page.tsx` | Editor 상태, 사진 순서 전달, 표지·ZIP 내보내기 |
| `components/ThumbnailEditor.tsx` | Fabric.js 캔버스, 텍스트 레이어, 이미지 조정, 2배 해상도 출력 |
| `next.config.ts` | 서버 API 없는 정적 export |

### 로컬 어댑터의 요청 문자열

기존 UI와의 변경 범위를 줄이기 위해 `demoFetch('/api/photos?...')` 같은 호출 형태를 유지합니다. 이는 `fetch`를 호출해 서버 API로 전송하는 것이 아니라, 문자열을 분기해 IndexedDB와 샘플 데이터를 읽는 일반 JavaScript 함수입니다. 이미지 내보내기 시에만 같은 출처에 번들된 샘플 SVG를 `fetch`합니다. 사용자 선택 사진은 Blob에서 직접 읽습니다.

### 저장 수명과 한계

Manager(Organizer·Editor)는 가로 1,200px 이상의 데스크톱 화면을 기준으로 합니다. 모바일 Manager는 제품 범위에 포함하지 않으며, 작은 화면에서 작업 패널을 재배치하지 않습니다.

- 저장 위치는 해당 Origin의 IndexedDB이며 계정·다른 브라우저·다른 기기로 동기화되지 않습니다.
- 새로고침과 페이지 이동 후에도 저장된 사진을 읽고 Blob URL을 다시 만듭니다.
- 데모 초기화는 사용자 사진 레코드를 지우고 Blob URL을 해제합니다. 기본 샘플 8장은 유지됩니다.
- 최적화하지 않은 파일은 원본 메타데이터를 포함한 채 로컬에 저장·다운로드될 수 있습니다. 실제 개인정보가 담긴 사진 대신 테스트 사진을 권장합니다.
- 한 장 12MB, 한 번 4장, 최대 40장의 체험용 한도를 둡니다. 저장 공간은 브라우저 정책과 기기에 따라 달라집니다.
- 사진 이름의 구분자를 정리하고 MIME에 맞춰 확장자를 생성합니다. 파일 바이너리를 보안 검사하는 업로드 서비스는 아닙니다.
- 공유 브라우저나 동시 탭 협업을 위한 제품이 아니며, 제출·정렬·편집은 단일 사용자 체험을 기준으로 합니다.
- Canvas 출력 폰트는 시스템 sans-serif를 사용하므로 운영 화면의 폰트와 다를 수 있습니다. 외부 폰트 요청은 없습니다.
- 공개 홈페이지는 기존 서비스의 메인 배경 사진과 제품 소개로 구성했습니다. 배경 사진은 픽셀과 원본 비율을 유지하고 EXIF 메타데이터만 제거했습니다. 기존 운영 홈페이지와 동일한 화면이라고 제시하지 않습니다.

## 향후 운영 서비스 개선 방향

전용 이미지 저장소와 썸네일 파이프라인, 구조화된 메타데이터, 영구 정렬 저장, 서버 검증 세션과 리소스 권한 확인, 분산 환경의 중복 요청 제어가 주요 후보입니다. 이는 공개 데모에 이미 적용된 기능을 뜻하지 않습니다. 실제 개선 우선순위는 운영 빈도·실패 로그·사용자 피드백을 수집한 뒤 정해야 합니다.
